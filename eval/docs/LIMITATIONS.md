# Limitations

Read this before quoting anything from this harness.

## No results exist

No subject agent exists, so there is no agent performance number on any suite. The oracle smoke is a
grader check. The layout sample is synthetic. Engine unit tests in `resolve/tests` are not agent evaluations.

## The AP fixtures

- 18 development fixtures, not sealed. They live in the same repo as the agent's code, anyone can read
  the private tree, and they have been looked at while building the grader. Treat scores on them as
  development signal only.
- One case per family, so family-level intervals are wide and one flipped case moves the rate by 5.6 points.
- Generated by one template (`data/engine/fixtures.py`). Amounts and ids vary, structure barely does.
  An agent can overfit the template.
- Seven of 18 cases are holds (four WAITING, three ESCALATED). An agent that marks everything WAITING with
  an owned issue scores 4 of 18 without doing any work. Read correct-escalation rate and unassisted
  completion separately, not just the total.

## The grader

- It grades an exported `CaseFinalState`. The adapter builds that export, so a dishonest or buggy adapter
  can misreport persisted state. Review the adapter. Prefer exporting straight from the backend database.
- `justified_hold` checks that an open issue names a responsible party and a next action. It does not check
  that the issue is the right issue for the case.
- Evidence sufficiency checks that required document ids are cited, not that they were read or understood.
- Hold cases only require the invoice to be cited.
- Duplicate messages are detected by `duplicate_of` or a repeated (role, correlation id, issue types) tuple.
  A legitimate reminder that reuses all three would be flagged.
- Cash-like economic events are detected by name (CASH, BANK, PAID, TRANSFER and similar).
- Over-escalating a resolvable case and mixing up WAITING with ESCALATED are both plain `fail`.
- The trace is recorded and counted, never scored.
- In paired comparisons an errored task is `unavailable`, while in pass rates an error counts as a failure.

## The runner

- No process isolation. The agent runs in a thread of the harness process and could read
  `data/generated/private` from disk. The workspace rules stop accidents, not a determined agent.
  Run real subjects in a container that mounts only the workspace.
- A timed-out agent thread is abandoned, not killed. It is asked to stop through `sandbox.cancelled()`.
- The spending cap depends on adapter-reported cost and is checked before each trial starts, so
  concurrent trials can overshoot it by up to `concurrency - 1` trials.
- The counterparty simulator returns staged documents for a trigger. It does not model time
  (`available_after` is ignored), unsolicited delivery, or a supplier who changes their answer.
  The agent has to ask with `supplier_unsolicited_reply` and `review_started` to receive those documents.

## Not implemented

- `crypto_native` (C01 to C12) and `reliability`: registered, no tasks, no loader, no grader.
- APEX and Invoice Sandbox: stubs. Their setup commands are blank until verified against the source.
- Finance Agent v1 and v2, BenchRec: register entries only.
- AccountingBench: never claimed. The planned substitute, the MIRROR longitudinal close suite, inspired by
  AccountingBench, does not exist.
- DABstep: exporter and a local approximate scorer only. The scorer is not the official one.
- Every external suite's owner, URL, revision, license, split and task count: pending source verification.
- Promotion gate thresholds: TODO for humans, see PROTOCOL.md.
